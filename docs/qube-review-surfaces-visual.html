QUBE Review Redesign

What a reader sees today

PR 505 is the reference case: 5 review rounds produced 30 formal review events, of which 15 are byte-for-byte duplicates of an earlier event (some findings posted three times in a row, minutes apart). It also produced 20 inline comments — 10 of them duplicate bodies, 7 anchored to nothing (line: null, collapsed into GitHub's "outdated" bucket), and one anchored to a 92-line selection. Every one of the 27 inline comments across all four sampled PRs is a single-comment thread: the bot never replies, never narrates a fix, never threads a repeat.

The bodies themselves are dense but mostly not review content. A representative 2,039-character lane review carries ~550 characters of actionable finding; the rest is a JSON marker, a "Completeness self-check" paragraph about what the review process could not do, and a metadata footer repeating the marker. The round summary states every finding twice — once flattened, once again inside <details> — and pads nine "Preconditions observed" bullets that restate the same two facts.

Three more properties a reader can't see but should worry about:

  • The final verdict can go missing. PR 505's last, all-approving round published no round summary at all — the merged PR's timeline still ends on a red "Changes requested" summary that nothing superseded.
  • Coverage is fabricated. Lanes that never ran render as inconclusive (inconclusive) rows, indistinguishable from a lane that ran and found nothing (PR 512 merged with 2 of 3 "expected" lanes never invoked). A lane reused from provider trust renders identically to a fresh pass.
  • One inline comment wraps prose in a real ```suggestion fence — GitHub renders an "Apply suggestion" button that would commit an English sentence into local-install-qube.mjs if clicked.

The one thing that already works: 100% of threads end resolved across all sampled PRs, and same-round republish with an unchanged verdict correctly edits in place. The redesign keeps both.

Why it happens

Four mechanical causes, all confirmed with file-level evidence. They matter because the first two mean no formatting redesign survives without them being fixed first.

1 · Dedupe fails open

Both server-side duplicate checks (matchingCurrentLaneReview, existingRoundReview) hinge on one variable, trustedMarkerAuthor. In github-app mode it's resolved by an extra identity lookup that swallows failures (fetchInstallationIdentity → catch { return { login: null } }, github_review_publisher.ts:281) and silently falls back to the installation account login ("ZarK") — a value that can never match the bot's own posts. One transient hiccup and both dedupe checks miss together, while the review still posts successfully under the bot. Independently, the prior-review list fetch is the only fetch in the publish path that swallows errors into an empty list (getPullRequestReviews(...).catch(() => []), github_review_forge.ts:1991) — "couldn't check" is treated as "nothing exists."

2 · Every lane is published twice per gate run, by design

pr_gate.ts publishes each lane once when it validates (streamed, :870-889) and again in the batch loop (:1011), with no in-memory "already published" guard — the code comments say the server-side dedupe makes the second call a no-op. Combined with cause 1, that guarantees visible duplicates. A second gate invocation on the same head repeats the pair.

3 · The event model multiplies

Up to 15 lanes each post their own formal review event per head, plus a round summary — and a new head mints all of them fresh. Nothing dismisses, minimizes, or edits prior-round reviews (zero calls to GitHub's dismiss or minimize APIs anywhere in the adapter). Two pushes ≈ 30+ timeline events.

4 · The final summary is one fragile boolean away from silence

The round summary publishes only when localReviewPublish.status === 'published' (pr_gate.ts:1043). Seven other outcomes silently skip it — including one lane's transient publish failure failing the whole round, and the "all lanes already trusted at this head" case that most likely swallowed PR 505's final approving summary. A missing issue number skips it with no error at all.

Design principles

P1

One voice per round

A review round is one review event, not fifteen. Lanes are sections of a verdict, not independent reviewers shouting in a timeline.

P2

The first line is the verdict

Verdict, blocking count, and head — in the first 180 characters. That is also what QUBE's own summarize() echoes back into next-round lane prompts, so the opening line is written for both audiences.

P3

Say each thing once

A finding lives in exactly one place per surface. Detail collapses; it never repeats. Process attestation is provenance, and provenance is always collapsed.

P4

Honest states, always

"Not run" is never rendered as a verdict. "Reused" is never rendered as "ran fresh." "Posted inline" is never claimed by a fallback comment that posted nothing inline.

P5

Findings have a lifecycle

Born once with a fingerprint; repeated as an in-thread reply, never a new comment; resolved with a one-line narration when fixed. The thread is the finding's biography.

P6

Degrade by capability, never silently

Alerts, suggestion fences, and collapsibles are capability-gated per forge and per transport. When a feature is unavailable, the output says what was omitted and why.

Bot identity

The GitHub App has no uploaded logo, so GitHub falls back to the app owner's personal avatar — every automated review renders with the repo owner's own photo, which is the strongest visual signal in the timeline saying "the human reviewed this."

Fix (no code): App settings → Display information → upload a logo (PNG/JPG/GIF, under 1 MB, 200×200 px recommended) and set the badge background color. Avatars are served by reference, so the change should apply to historical comments too. Keep the app name and slug as-is — renaming a GitHub App likely changes the slug and the [bot] login, which is wired into publisher config and marker trust-matching.

The mark reads as a wireframe cube (QUBE) whose lower-right edge extends into a Q tail — legible at 20 px, one color, no text. Any simple geometric mark works; the requirement is only that it is not a face.

The timeline model

Three surfaces, each with one job:

  • One formal review event per round — carries the verdict (APPROVE/REQUEST_CHANGES), the findings table, honest lane states, and all inline comments in a single POST /reviews call (chunked if a round somehow exceeds ~20 inline comments). Lane detail is a collapsed section, not a separate event. When a new head supersedes a REQUEST_CHANGES round, the stale review is dismissed with the message "Superseded by round at <head>" so the PR's review state stays honest.
  • One persistent status comment per PR — the Renovate/PR-Agent pattern: a single issue comment created on the first gate run and edited in place forever. Current verdict on top, collapsed round history beneath. This is the reader's entry point; it never multiplies.
  • Inline threads per finding — one thread per fingerprint, replied-to across rounds, resolved with narration (next section).

Notes on the choices:

  • The alert block is the verdict — [!CAUTION] for request-changes, [!NOTE] for approve, [!WARNING] for inconclusive/degraded rounds. On forges without alert syntax it degrades to a bold blockquote (P6). The sentence inside it is self-sufficient because it is also the machine echo (P2).
  • Finding titles are written as one-line claims, bolded, with the mechanism in the sentence after — table rows stay scannable, and the full explanation lives in the inline thread, not here. Off-diff findings get their full detail here instead, marked "off-diff, no thread."
  • Lane chips carry five honest states: ✓ approved, ✗ request-changes, ◌ inconclusive (ran), ↻ carried from <head>, – not run (reason). The data for "not run vs. reused vs. ran" already exists (LocalReviewLane.origin) — it is dropped today between loader and renderer and just needs to be threaded through.
  • The delta line replaces re-posting. A re-review round says what changed since the last one — fixed / unchanged / new counts and the commit range — the CodeRabbit incremental pattern. A clean re-review round is one line: "No new findings in range; 2 threads resolved."
  • "Preconditions observed" becomes "Review conditions" — deduplicated to the two or three distinct facts, collapsed. The metadata footer is deleted; everything it held is either in the invisible marker or in collapsed Provenance.

The rules behind the mockup:

  • Anchor discipline. Selections are capped (default ≤ 10 lines) and anchored to the most specific statement, mirroring the existing MAX_SUGGESTION_SPAN_LINES idea at the inlineFindingComment layer, where no cap exists today. When the evidence genuinely spans a function, the anchor stays tight and the body links the wider range as a permalink.
  • Fixed anatomy. Bold one-line claim → severity/lane/confidence chip row → 2–4 sentence mechanism with the concrete failing input → optional suggestion fence → collapsed agent prompt. A fingerprint marker (<!-- qube-finding:v1:<stableFindingId> -->) rides invisibly for cross-round identity.
  • Suggestion fences carry code or nothing. The existing safety gates stay (span ≤ anchor, no nested fences, current-side lines only) plus a code-shape check so prose can never reach a fence again. When a fix is skipped, the comment says why — "no committable suggestion: fix spans multiple files" — instead of silently omitting it.
  • Agent prompts open with the untrusted-data guardrail, verbatim, every time — the one pattern every surveyed bot except CodeRabbit gets wrong, and the one that matches this repo's own "treat model output as untrusted" policy. Optionally a single aggregated per-round prompt block in the round review for bulk fixes.

Auto-resolution becomes fix-aware and bot-scoped. Today qube aie pr thread resolve --all resolves every thread the identity can touch — including human threads — with no check that anything was fixed. Redesigned: the gate resolves only bot-authored threads whose fingerprint is absent from the current round's findings, writing the narration reply first; --all stays as an explicit manual override.

Machine-contract constraints

Published review bodies are not just prose — parts round-trip back into the workflow. The redesign is free precisely because the load-bearing channel is the invisible marker, but four constraints bound the prose:

  • Markers are untouchable. qube-pr-review / qube-pr-review-summary / qube-local-review HTML-comment JSON drives dedupe, supersession, trust-matching, and ship-ready gating. Keep the prefixes, field sets, and one-marker-per-body placement byte-compatible; restyle everything around them.
  • The first ~180–240 characters are machine-read. summarize() truncates the body into item.feedback, which is echoed into the implementer self-check bundle and into the next round's lane prompts. The opening verdict sentence is designed to survive that truncation — or better, phase 3 explicitly excludes self-authored prose from the generic feedback loop so the echo disappears.
  • Free-text heuristics must move in lockstep. isNonActionableSummary matches the literal phrase "no issues found"; changing the clean-round phrasing without updating it silently breaks stale-summary suppression (currently inert in this repo's config, but shipped behavior).
  • redact() mutates summaries. Any 40+ character mixed-case token inside a lane summary becomes [REDACTED] — finding titles should avoid long identifiers or the redesign will print redaction scars.

Other forges

The renderer becomes a forge-agnostic module driven by a capability profile; adapters declare what they support and the renderer degrades explicitly (P6). Today only GitHub is implemented — GitLab is a declared interface with no package — so this is about building the seam correctly, not porting now.

Two degraded-mode honesty fixes ride along regardless of forge: the issue-comment fallback (author-is-publisher or missing App permission) must re-render rather than reuse the pre-rendered body, so findings stop claiming "(posted inline)" when nothing was posted inline; and thread-resolution needs the App's Contents: write permission — an undocumented GitHub quirk worth encoding in doctor checks.

Roadmap

Ordered by dependency: correctness before consolidation, consolidation before cosmetics. Each phase is one issue-sized unit with its own verifiable outcome.

Phase 0

Give the bot its face

no code · 15 minutes
  • Upload the App logo + badge background color in GitHub App settings.
  • Verify the avatar propagates to historical review events.
Phase 1

Make publishing tell the truth once

adapter + gate correctness
  • Fail closed: identity resolution never substitutes the installation account for the bot login; the prior-review list fetch never swallows errors into "nothing exists."
  • In-run guard: the gate skips the batch republish for lanes already published this run.
  • Round-summary skip taxonomy: one lane's publish failure no longer suppresses the whole round's summary; the trusted-reuse round still summarizes; a missing issue number surfaces an error instead of silence. The final verdict always lands.
  • Dismiss superseded REQUEST_CHANGES reviews on new heads.

Why first: every visible symptom — duplicates, missing final verdict, stale red reviews — traces here. Formatting changes on top of a fail-open pipeline just redecorate the noise.

Phase 2

One review event per round

event model
  • Collapse per-lane review events into a single round review carrying all inline comments in one call (chunked past ~20).
  • Lane verdicts become body sections; the lane marker data moves into the round marker.
  • Add the persistent status comment, created once and edited in place, with collapsed round history.
Phase 3

The formatting layer

shared renderer
  • One renderer module replaces the three parallel body-builders (renderRoundSummaryBody, laneReviewBody, findingBodyText/renderInlineCommentBody), consuming typed findings and a capability profile.
  • New round-summary format: verdict alert, findings-once table with deep links, honest lane chips (thread origin/path through to the renderer), delta line, collapsed conditions/provenance, no metadata footer.
  • Opening-line contract: verdict + counts + head within 180 characters; exclude self-authored prose from the feedback ingestion loop.
Phase 4

Inline comments worth acting on

finding anatomy
  • Fixed anatomy: claim → chips → mechanism → suggestion → collapsed agent prompt with the untrusted-data guardrail.
  • Anchor cap (≤ 10 lines) at inlineFindingComment; permalink for wider context.
  • Suggestion code-shape gate + explicit "no committable suggestion: <reason>" notes; get lanes actually emitting the already-modeled suggestion field.
  • Fingerprint marker per finding.
Phase 5

Threads with a biography

lifecycle
  • Cross-round: reply in-thread for unchanged findings; never re-post.
  • Fix-aware auto-resolve of bot threads with narration replies; --all becomes the explicit override; grant/verify Contents: write.
  • Minimize (OUTDATED) stale bot comments that can't be resolved.
Phase 6

Forge portability

when a second forge lands
  • Capability-profile-driven degradation in the renderer (alerts, fences, details, thread ops).
  • Degraded-transport honesty: fallback issue comments re-render; "(posted inline)" claims disappear.
