QUBE

QUBE is a set of command-line tools for agent-assisted work in a git repository. It has four parts: Bootstrap, Executor, Quality and Umpire. Each part is its own npm package and works on its own. The qube command runs whichever parts are installed.

Each tool reads and writes state in the repository, under .qube/ and in the work provider, and has a --json output for scripts and agents. An agent working through QUBE leaves the same records a person would check: issues, branches, pull requests, gate results and review threads.

BootstrapPlan the work
ExecutorDo the work
QualityCheck the work
UmpireDecide whether to continue

The four parts

The name comes from their initials: Quality, Umpire, Bootstrap, Executor. In practice work moves through them as Bootstrap, Executor, Quality, then Umpire.

Bootstrap

@tjalve/aib · aib

Turns an idea into planning state: a spec, milestones and drafts of work items. Another tool or agent can pick these up later.

Input
An idea in plain text.
Output
A spec, milestone plans and work item drafts that can be published as issues.
qube aib init . --idea "Ship a local notes CLI" --json
qube make-it-so --flow planned "Ship a local notes CLI" --json

Executor

@tjalve/aie · aie

Runs issue-driven work: finds ready issues, starts a scoped branch, runs the repository's gates, opens the pull request, gathers reviews and completes the issue after merge.

Input
Ready issues from GitHub, GitLab, Linear or Jira, through an adapter package.
Output
Branches, pull requests, review rounds and completed issues.
qube aie queue --json
aie pr gate 732          # run the review lanes and publish the result

Quality

@tjalve/aiq · aiq

Runs code quality checks in stages. The repository stores its current stage, and each run uses the repository's own tool configs: Biome, TypeScript, Vitest or Jest, Playwright, Ruff and others.

Input
The repository's existing tool configs.
Output
Gate results as structured evidence that people and agents can both read.
qube aiq doctor --format json

Umpire

@tjalve/aiu · aiu

Decides whether an idle agent may continue. It reads state from commands you trust, not from what the agent says about itself. When the next step is clear enough, it writes the prompt. Otherwise it stops.

Input
Output from trusted state commands, plus a continuation policy.
Output
A concrete next prompt, or a stop with the reason. Unknown, stale or blocked state counts as a stop.
qube aiu status --json

How they connect

  1. Bootstrap turns an idea into a spec and work items, then publishes them as issues.
  2. Executor takes a ready issue, starts a branch and has an agent implement it.
  3. Quality runs the gates for the current stage. Executor opens the pull request, and QUBE Review reviews it.
  4. Executor handles review findings, merges and completes the issue.
  5. Umpire checks trusted state when the agent goes idle. It lets the agent continue with a specific prompt, or stops.

Install and set up

Install an exact version. A project install is the most reproducible choice for automation. QUBE 0.2.12 is the version these examples pin. The main branch is the development version and can have commands that are not in that release.

# project install
pnpm add --save-dev --save-exact --ignore-scripts @tjalve/qube@0.2.12
pnpm exec qube init --dry-run --json
pnpm exec qube init

With npm, use npm exec -- qube init. For a global install, run qube init directly. Each part can also be installed on its own, for example @tjalve/aiq.

Before you start

  • Node.js 24 or newer and Git 2.28.0 or newer.
  • At least one supported agent host, installed and signed in.
  • The CLI for your work provider, such as GitHub CLI signed in to github.com.
  • The repository's primary checkout. QUBE can create a Git repository with --git-init, but it never creates commits, remotes or accounts.

What qube init does

A guided setup that asks only the questions that apply to the repository. It shows the full plan before it writes anything. --dry-run --json prints the resolved answers without changing files. --yes accepts the recommended values for non-interactive setup. Running it again keeps valid current values and changes nothing if they all match.

  1. Repository checks. Git version, commit identity, branch, base and working tree. A missing author name or email is asked for and written only after you confirm.
  2. Hosts. Which agent hosts you use, which one is primary, and where reviews run: inside the primary host, or isolated in a separate read-only CLI session.
  3. Providers. The issue tracker, the source of automated checks, Continuous Shipping, Umpire continuation, Quality stages, and the review publisher.
  4. Products. Bootstrap prepares planning. Executor prepares issue work, checks, review and shipping policy. Quality prepares its stages. Umpire prepares the continuation scope.
  5. Host files. Writes the instruction file and the make-it-so entry point for each selected host. It only includes behavior that host supports.

Settings live in .qube/init.json for the repository, or ~/.qube/config.json with qube init --global. Repository values override global ones. QUBE stores credential references, never the credential values.

After setup

# connect the QUBE Review GitHub App and check it is ready
qube review setup github-app --app-id 123456 --installation-id 789012 \
  --private-key-path "$HOME/.config/qube/reviewer.pem" --yes
qube review doctor --json

# pick work
qube queue --json
qube start 123 --json

# change hosts later without rerunning init (development)
qube hosts --host codex,cursor --review-mode isolated --review-harness cursor --dry-run --json

# when an agent goes idle
pnpm exec qube continue --json

Then open a new session in your agent host so it loads the new instructions, and send the start command, for example $make-it-so Complete issue 123, then stop. in Codex. Depending on repository policy, the agent can implement the issue, run the checks, get the pull request reviewed, merge it and close the issue. The first-task guide walks through this with Codex and GitHub.

Hosts and providers

A host is the agent tool that runs the session: it owns the model, tasks, subagents and hooks. QUBE writes its instructions and configuration, then calls QUBE commands from inside it. QUBE does not install, sign in to, or wrap a host. Each host and provider has its own adapter package, so you install only the ones you use.

QUBE Review

QUBE Review is the pull request reviewer that comes with Executor. aie pr gate runs a set of review lanes on the pull request head. Each lane is an agent with one focus. The results go back to the pull request as a single review from the QUBE Review GitHub App.

The review is written so a person can read it quickly, and so the next agent round can read it back. The first line gives the verdict. Each finding appears in one place. Details are collapsed.

issue-compliancecode-qualitysecurityperformancetests-qualitydocs-instructionserror-observabilityconcurrency-resourcedata-databaseui-ux-accessibilityrelease-ci-supply-chainmanual-qafinal-gate
  • Publisher: the qube-review[bot] GitHub App, with its own avatar.
  • Per round: one review event per pushed head. A newer head supersedes and dismisses the previous request-changes review.
  • Profiles: focused runs a few lanes picked by risk. Comprehensive runs every lane.
  • Lane states: approved, request-changes, inconclusive, carried from an earlier head, or not run with a reason.
  • Other forges: GitLab, Gitea and Bitbucket use the same renderer. Features a forge lacks are left out, and the review says which ones.

The round review

One review per round. The alert line carries the verdict, the counts and the head. The findings table lists each finding once, with a link to the code and its inline thread. Lane notes, review conditions and provenance stay collapsed. The text below is from a real round on pull request 732, shortened.

Inline comments

Each finding on the diff gets one inline comment, always in the same order. First the claim in bold, then severity, lane and confidence, then how it fails with a concrete input. After that comes a committable suggestion, or a short reason why there isn't one, and finally a collapsed fix prompt for agents. Selections cover at most 10 lines.

Thread lifecycle

Every finding has a fingerprint, so later rounds can follow it from one round to the next.

EventWhat QUBE Review does
New findingOne inline comment with a fingerprint marker.
Still present next roundReplies in the existing thread. It does not open a new comment.
FixedReplies "Fixed in <sha>", then resolves the thread.
Dropped or triaged outReplies with the reason, then resolves.
Round supersededDismisses the stale request-changes review.

It only resolves its own threads. See QUBE Review Surfaces for the full format and the machine-readable markers.
